# Roadmap

A lighter-weight, forward-looking summary of what's planned. For detailed technical context on the original modernisation plan items, see [docs/napari-clemreg-modernisation-plan.md](docs/napari-clemreg-modernisation-plan.md) — this document links to the relevant section of that plan where one exists, and additionally covers newer ideas that have come up since it was written, from live GUI testing.

See [CHANGELOG.md](CHANGELOG.md) for what's already landed.

## Known GUI bugs

Each is pinned by a strict expected-failure test (in `test_widget_behaviour.py` or `test_pipeline_baseline.py`). Phase 1 of the package split (#58) fixes #47 by design.

- **Save parameters crashes Register, and Parameters from JSON does nothing** ([#47](https://github.com/martlj/napari-clemreg/issues/47)).
- **Voxel Size sits in the wrong section** ([#49](https://github.com/martlj/napari-clemreg/issues/49)).
- **Registration direction EM → FM always crashes** ([#68](https://github.com/martlj/napari-clemreg/issues/68)), in every release so far. Fixing it needs a decision on what EM → FM output should look like.
- **README screenshots are out of date** ([#51](https://github.com/martlj/napari-clemreg/issues/51)).
- **Register reports a failed segmentation twice** ([#85](https://github.com/martlj/napari-clemreg/issues/85)): its segmentation workers connect `errored` after creation, so superqt's re-raise also fires.
- **Importing the plugin freezes napari for about 3.5 s, even to open a TIFF** ([#86](https://github.com/martlj/napari-clemreg/issues/86)): `__init__.py` imports every widget, which loads open3d and probreg. `run_registration.py` also edits `sys.path` on import.

## Planned

From the original modernisation plan (`docs/napari-clemreg-modernisation-plan.md`):

- **Repository & release strategy** ([#1](https://github.com/martlj/napari-clemreg/issues/1), plan §7) — when/how `modernisation` goes back into `main` (it's the fork's default branch meanwhile), actual version tagging, PyPI ownership transfer to the Crick org. See the "Status note" at the top of [CHANGELOG.md](CHANGELOG.md) — no version bump has actually happened yet despite several release-worthy batches of work (proposed numbering in the CHANGELOG).
- **`empanada-dl` dependency blocker** ([#5](https://github.com/martlj/napari-clemreg/issues/5)) — still can't install on Python 3.11 (`numpy==1.22` pin, no wheels). Segment-Flow (0.5.0) makes this non-blocking for EM segmentation generally, but the extra itself is still broken for anyone who specifically wants the in-process bundled backend.
- **MoBIE project output option** ([#6](https://github.com/martlj/napari-clemreg/issues/6), plan §3) — export registered/warped volumes as a MoBIE project. Now part of the [OME-Zarr design](docs/design/ome-zarr.md) (phase 5), which writes the OME-Zarr itself and generates the MoBIE metadata from it.
- **napari hub and PyPI listing** ([#87](https://github.com/martlj/napari-clemreg/issues/87)): absolute URLs for the README images, which are broken on PyPI and the hub today; delete the unused `.napari/` folder; add a manifest `display_name` and `categories`.
- **Cancelling Segment-Flow runs and cleaning up closed widgets** ([#88](https://github.com/martlj/napari-clemreg/issues/88), needs a decision on a Cancel button): `quit()` can't stop the Nextflow subprocess, and nothing is released when a dock is closed.
- **Package split: `clemreg` core + `napari-clemreg` widgets** ([#7](https://github.com/martlj/napari-clemreg/issues/7), [milestone *clemreg 0.1.0*](https://github.com/martlj/napari-clemreg/milestone/1)): design in [docs/design/package-split.md](docs/design/package-split.md), with phases #58–#61 (decisions agreed in #57). MoBIE export (#6) is written directly in the core and can start once phase 1 (#58) merges. Get the upstream owner's agreement to the new layout before phase 2 (#59). If they decline it, the fallback is a separate `clemreg` repository in the Crick org (D1).

## Newer ideas (from live testing, not in the original plan)

- **Selectable point cloud sampling methods** ([#75](https://github.com/martlj/napari-clemreg/issues/75)): design in [docs/design/point-sampling.md](docs/design/point-sampling.md). Today points come only from the outside edge of each mask (2D Canny per z-slice) after nearest-neighbour resampling, so on anisotropic data they sit in terraces at the original z slices and miss the top and bottom of each object. The current method stays the default, with unchanged results. The design adds a `continuous` method: shape-based interpolation of each object's signed distance on its native grid, then points drawn at continuous positions from a density over depth, tuned by one `position` setting from surface to centreline (or uniform), with *Surface*, *Centreline* and *Throughout* presets. It covers #75's distance-weighted and skeleton methods; object centroids stay as a baseline. It starts with a prototype and evaluation on synthetic phantoms (phase 0). Decisions P1–P6 in the design doc are proposed, apart from keeping `edge` as the default.

  Package the samplers so other projects can import them with only numpy, scipy and scikit-image, i.e. without open3d or the registration stack. Where they live is open decision D9 in the [package split design](docs/design/package-split.md#decisions-log).

- **Automatic initial orientation for point cloud registration** ([#73](https://github.com/martlj/napari-clemreg/issues/73)). Registration works much better when the clouds start within about 90° of the right orientation, and today users pick the nearest orthogonal orientation by hand. The same coarse step would also let an EM volume much smaller than the FM field (e.g. 10 µm in 200 µm) be found automatically. The [feasibility notebook](notebooks/global_registration_feasibility.ipynb) compared methods on synthetic data. Template matching over in-plane rotations and a mirror worked when EM and FM share roughly the same z axis, even for 10 µm EM fields. RANSAC on FPFH features needed a rough position and an EM field of about 50 µm to cope with any orientation. Multi-start CPD failed when the FM field is much larger than the EM. Still to do:
  - template matching for each of the 6 choices of which EM axis maps to FM z, to handle 3D orientations for small EM fields
  - repeat on real FM/EM pairs, starting with sub-volumes of the sample data
  - multi-start CPD on fields of view that mostly overlap, which the notebook didn't test
  - a rough position as an optional napari Points input, since both methods that worked do better with one
  - handling a z flip between EM and FM, as a user setting or as extra candidates (the notebook tries both and keeps the better fit)
  - check whether clemreg's own refinement is affected by two problems the notebook found. From the true pose, rigid CPD drifted by up to 2.8 µm and 10° on clouds sampled per z slice, while ICP stayed put. And open3d's normals lean towards each cloud's own +z, which makes FPFH features depend on the frame. The continuous sampling design (#75) may help with the first.

  It fits the core's `register_point_clouds`, and is easier after package split phase 1 (#58).

- **2D registration** ([#79](https://github.com/martlj/napari-clemreg/issues/79)). A single EM section with a single FM plane, including multichannel FM. Today every step assumes (z, y, x): the FM filter and TPS warp hardcode three axes, segmentation thresholds each z slice, sampling runs Canny per slice and builds open3d 3D clouds, and resampling, warp matrices and output shapes are all 3D. A 2D pair should run through the same widgets and core API, with transforms limited to the plane: rigid is a rotation about z plus translation (and scale), affine is 2×3, and BCPD deforms only within the plane. Plan:
  - **Dimensionality is explicit, not guessed from `ndim`.** The reader squeezes size-1 axes, so a (c, y, x) FM image looks like a (z, y, x) stack. Keep bioio's dimension names in layer metadata and decide 2D or 3D from those, with a widget override when the metadata is missing. `PixelSize` allows no `z` for 2D.
  - **Design the phase 1 types (#58) to cover 2D**, so this doesn't break the API later: `Transform` has an `ndim` and holds a 3×3 or 4×4 homogeneous matrix (or 2D or 3D control points), and `Result` and the MoBIE exporter (#6) take it from there.
  - **Segmentation:** use a 2D difference of Gaussians (`_diff_of_gauss_2d` already exists), threshold the whole image rather than each row, and let `MaskRoi` have no z range. MitoNet is a 2D model, so both EM backends should accept one section.
  - **Sampling:** run Canny on the image directly. Pad clouds with z = 0 for open3d's downsampling and outlier removal, then drop the column, or replace those with numpy/scipy as part of #75.
  - **Registration:** register 2D clouds natively instead of as flat 3D clouds, which can rotate out of the plane. Checked against probreg: BCPD and affine CPD work on (N, 2) points (affine needs 2×2 initial parameters passed in), but rigid CPD crashes in 2D because its reflection fix hardcodes three dimensions. Options are an upstream fix, a small local 2D rigid step, or embedding in 3D and projecting the result back onto an in-plane rotation.
  - **Warping:** 3×3 matrices through `ndimage.affine_transform`, a 2D version of `_rescale_affine_matrix`, and a TPS warp written for any number of dimensions. The working grid becomes the EM xy pixel size, since there's no EM z pixel size to use.
  - **Widgets:** hide the z range and z pixel sizes for 2D inputs, and show 2D points and outputs.
  - **Tests:** synthetic 2D pairs with a known rotation, translation and shear that each algorithm must recover, plus a 2D slice of the sample data as a smoke test. The 3D output baseline must stay unchanged.
  - **Later:** automatic initial orientation (#73) in 2D has 8 candidates (4 rotations, with and without a flip), not 24. Registering a 2D EM section to a 3D FM stack (slice-to-volume) is a separate problem and out of scope; until then, mixed 2D and 3D inputs should fail with a clear error.

  Best done after package split phase 1 (#58), since it changes every core function's signature, but the types should be decided in phase 1.
- **Nextflow pipeline for batch and HPC runs** ([#91](https://github.com/martlj/napari-clemreg/issues/91), needs decisions). A Nextflow version of the full workflow, alongside the plugin rather than replacing it: tune parameters and draw the Mask ROI on one dataset in napari, save them to files, then run many FM/EM pairs on a cluster. The steps already form a simple chain (FM segmentation, EM segmentation, point cloud sampling, registration, warping), and EM segmentation already runs through Segment-Flow, so the pipeline can reuse its `local`, `crick` and `rosalind` profiles. `-resume` would cache EM segmentation, the slowest step, so registration settings can be re-run or swept without segmenting again. Separate environments per process would also keep empanada's numpy pin (#5), open3d's libusb requirement and the torch/OpenMP clash apart. For a single dataset on a laptop the plugin stays the better tool, since Nextflow needs a JDK and adds its own overhead. Plan:
  - **Prerequisites:** package split phase 1 (#58) for napari-free core functions and `Params.to_json`/`from_json` (#47 blocks saving tuned parameters today), and the headless `run_clemreg` (#60). Phase 2 (#59) helps containers install the core but isn't strictly needed.
  - **A `clemreg` CLI with file inputs and outputs**, useful on its own too: `segment-fm`, `segment-em` (or a precomputed `--mask`), `sample`, `register`, `warp` and `run`. `Params` and `MaskRoi` as JSON, point clouds as `.npy`, and `Transform` as JSON or `.npz` covering both affine matrices and TPS control points. Running the synthetic baseline (`test_pipeline_baseline.py`) through the CLI must give the same values.
  - **Environments:** a CPU container for the core (open3d, probreg), published to ghcr, with EM segmentation keeping Segment-Flow's own per-model environments on a GPU label. This would replace the outdated Python 3.9 GUI `clemreg.dockerfile` for batch use.
  - **The pipeline (DSL2):** a samplesheet (`sample_id, fm_path, em_path`, plus optional `em_mask`, `roi` and per-sample `params`), and the processes `SEGMENT_FM`, `SEGMENT_EM` (skipped when a mask is given), `SAMPLE_POINTS`, `REGISTER`, `WARP` (one task per channel) and `QC` (overlay images, plus metrics such as inlier fraction or Chamfer distance, so failed registrations stand out in a batch). Later `EXPORT_MOBIE` (#6).
  - **Tests:** nf-test on the synthetic data, and a CI job with Nextflow installed, which would also let the real Segment-Flow test stop skipping on CI.
  - **Plugin link (optional):** an *Export batch config* button that writes the tuned params, ROI and a samplesheet row. Launching runs from napari should wait for the cancellation decision in #88.
  - **Later:** parameter sweeps, the multi-start orientation search (#73) as a scatter-gather step, and OME-Zarr intermediates instead of large TIFFs between processes.

  Open decisions: whether the pipeline lives in its own repository (e.g. in the Crick org next to Segment-Flow) or in a `pipeline/` folder here; whether Segment-Flow is included as a subworkflow (not yet checked whether 0.2.1 supports `include`) or version 1 requires a precomputed EM mask, since running Nextflow inside a Nextflow process causes problems with scheduling, caching and cancellation; containers, conda or both for the core; and leaving EM → FM (#68) out of version 1.
- **Organelle presets: choose what to segment** ([#102](https://github.com/martlj/napari-clemreg/issues/102), needs decisions). An *Organelle* choice at the top of Run Registration that fills in a suitable FM method, EM model and defaults, while any setting can still be changed and users can still bring their own masks. Presets:
  - *Mitochondria*, the default: LoG on FM (sigma 3, threshold 1.2) and MitoNet v1 on EM, exactly as today, so the output baseline doesn't change. The AIoD registry has no FM mitochondria model, so LoG stays; a learned FM model can be added later as another FM method.
  - *Nuclei*: Cellpose-SAM (`cpsam`, task `nuclei`) on FM and NucleoNet v1 (`empanada`, task `nuclei`) on EM, both through Segment-Flow. Both names are in `aiod_registry` 0.2.0.
  - *Custom*: any FM method or registry model, or existing masks.

  Plan:
  - **Run any registry model through Segment-Flow.** `segment_flow_segmentation.py` hardcodes `--model empanada`, reads its default config from the empanada manifest, patches empanada's `conf_threshold`, and looks for output in the empanada folder. Pass the model, model type, task and config overrides instead. Also give each run its own output: today it takes the last `*_all.tiff` by name from the shared cache, and every input is called `input.tif`, so it can return an earlier run's mask. Check how Segment-Flow runs Cellpose-SAM on a 3D FM stack (per slice or 3D, anisotropy, label stitching across substacks).
  - **Core API:** `segment_fm` gains a method choice (`log`, or a Segment-Flow model) and `segment_em` a model choice, both described by a small model-spec type (model, model type, task, overrides). The empanada backend stays MitoNet-only unless empanada-dl's NucleoNet works in-process too. `NoSegmentationError` names the organelle rather than mitochondria.
  - **Presets are data in the core**, mapping each organelle to its FM method, EM model and default parameters (FM settings, size filter, sampling frequency, point cloud sigma), so the CLI (#91) and the headless `run_clemreg` (#60) use the same ones.
  - **`Params` records the organelle and both model specs**, so a saved parameter file (#47) reproduces the run. Decide these fields in package split phase 1 (#58), so they don't change `Params` again later.
  - **Widget:** the *Organelle* dropdown fills in the FM and EM sections. *LoG Segmentation Parameters* becomes *FM Segmentation*, with the LoG fields shown only for LoG, and *EM Segmentation Backend* becomes a model choice plus backend.
  - **Bring your own masks.** Segmentation layers can already be picked in *Point Cloud Sampling* and run with its step button, but **Register** always segments both images. Add a per-side choice, *run a model* or *use an existing Labels layer*, so Register can take masks from another plugin or an earlier run for one or both sides.
  - **Nuclei change the registration problem.** A few large, nearly convex objects constrain registration much less than many mitochondria, and an EM field may hold only part of one nucleus. Tune the preset's sampling and size filter on real data, warn when there are too few objects, and see whether #75's sampling methods help.
  - **Tests:** the Mitochondria preset equals today's defaults; selecting a preset sets the widget fields; Register passes the model specs to the stubbed adapters and skips segmentation for a supplied mask. A slow test runs Nuclei on the sample data, which has an `FM_Hoechst` channel (still to check: how much nucleus the EM crop contains).
  - **Later:** more presets from the registry where an FM counterpart exists, e.g. lipid droplets (DropNet v1 on EM), or ER and nuclear envelope (SEAI U-Net). Registering on several organelles at once is out of scope.

  Best built after package split phase 1 (#58), since it changes `segment_fm`, `segment_em` and `Params`. The Segment-Flow generalisation has no napari code and can go first. Open decisions: whether picking a preset overwrites values the user has edited, or asks first; whether Register uses an existing mask because of an explicit setting or because the segmentation field is filled in (explicit is safer, since earlier runs fill those fields automatically); and whether needing Nextflow for FM segmentation too is acceptable, or Cellpose-SAM should also run in-process as an extra.
- **OME-Zarr input and FAIR project output**: design in [docs/design/ome-zarr.md](docs/design/ome-zarr.md). Open any bioio-readable input, including OME-Zarr 0.4 to 0.6. Convert other formats to sharded OME-Zarr 0.6 when a project is made, and link existing OME-Zarr instead of copying it. Store the registration as RFC-5 transforms. Write a project that is also a MoBIE project and an RO-Crate. It starts with a compatibility check ([#93](https://github.com/martlj/napari-clemreg/issues/93): do MoBIE, napari and bioio read 0.6 yet, and can MoBIE show BCPD results without resampling?), then runs in phases after package split phase 1 (#58), and replaces the exporter design in #6. Decisions D1–D12 in the design doc are proposed, not yet confirmed.
- **OME-Zarr sample data, tiff + zarr variants** ([#41](https://github.com/martlj/napari-clemreg/issues/41)): phase 8 of the OME-Zarr design, published as a sample CLEM-Reg project.
- **Regenerate EM sample data with real embedded pixel-size metadata** ([#42](https://github.com/martlj/napari-clemreg/issues/42)) — confirmed directly that the current EM Zenodo file has no pixel-size metadata embedded at all; the hardcoded override in `sample_data.py` is load-bearing, not decorative, and can't be retired until this happens.
- **Reconsider `ndevio` for broader file-format reading** ([#40](https://github.com/martlj/napari-clemreg/issues/40)) — a bioio-based reader with real "install missing format plugin" prompting, useful once we need formats beyond TIFF (CZI, ND2, LIF, OME-Zarr). Not adopted now: its reader registers for `.tif`/`.tiff` too, which would conflict with our own TIFF reader from #37.
- **magicgui vs. raw Qt for the widget layer** — investigated while building #35's per-section buttons: `make_run_registration()`'s own function body has no reference back to its own widget Container (confirmed directly against magicgui's internals — it's called as a plain function, no self-injection), which forced a workaround (watching `viewer.layers.events.inserted` and matching by layer name) instead of a direct call. AIoD's own `aiod_napari` plugin is built entirely in raw Qt and doesn't hit this class of problem at all, at the cost of losing magicgui's automatic type-based widget generation and layer-list choice syncing. Not worth a full rewrite now. It's recorded as decision D8 in the [package split design](docs/design/package-split.md#decisions-log): the split's adapters don't depend on either framework, so this can be decided after the split.
- **Push BCPD's warp fully upstream** (follow-up to [#33](https://github.com/martlj/napari-clemreg/issues/33)) — the Rigid/Affine CPD case warps directly from raw data in one pass, but BCPD doesn't yet, since it needs a bigger change to the TPS grid-generation code in an already-fragile area.
